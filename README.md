# gitops-demo

A complete local GitOps workflow using **FluxCD**, **Helm**, and **Kind** — where every change to the cluster goes through Git, never `kubectl apply`.

---

## What this demonstrates

- Packaging an app as a Docker image and loading it into a local Kind cluster
- Defining application state as a Helm chart with GitOps-managed values
- Bootstrapping FluxCD to watch a GitHub repository and reconcile the cluster automatically
- Making a real GitOps change (scaling replicas) by committing to Git and watching Flux apply it

---

## Stack

| Tool | Role |
|------|------|
| Docker | Container runtime |
| [Kind](https://kind.sigs.k8s.io/) | Local Kubernetes cluster |
| [Helm](https://helm.sh/) | Kubernetes package manager |
| [FluxCD](https://fluxcd.io/) | GitOps continuous delivery |
| GitHub | Source of truth for desired cluster state |

## Prerequisites

```bash
brew install colima docker kubectl helm kind
brew install fluxcd/tap/flux
```

Start Colima (skip if using Docker Desktop):

```bash
colima start --cpu 4 --memory 6 --disk 60
```

You also need a [GitHub personal access token](https://github.com/settings/tokens) with `repo` scope.

## Setup

### 1. Create the cluster

```bash
kind create cluster --name gitops-demo
kubectl get nodes
```

Expected output:
```
NAME                          STATUS
gitops-demo-control-plane     Ready
```

### 2. Build and load the app image

```bash
docker build -t demo:v1 ./app
kind load docker-image demo:v1 --name gitops-demo
```

> Kind clusters are isolated from your local Docker daemon. `kind load` is required — otherwise Kubernetes can't pull the image.

### 3. Validate the Helm chart

```bash
helm lint demo-app
helm template demo-app ./demo-app   # preview rendered manifests
```

### 4. Install Flux and pre-flight check

```bash
flux install
flux check
```

Fix any issues flagged by `flux check` before bootstrapping.

### 5. Bootstrap Flux to GitHub

```bash
export GITHUB_TOKEN=<your-token>

flux bootstrap github \
  --owner=<your-github-username> \
  --repository=gitops-demo \
  --branch=main \
  --path=clusters/dev \
  --personal
```

This will:
- Create the GitHub repo if it doesn't exist
- Install Flux controllers into the `flux-system` namespace
- Commit the Flux manifests to your repo
- Set up a deploy key so Flux can pull changes automatically

Verify controllers are running:

```bash
kubectl get pods -n flux-system
```

## HelmRelease — the GitOps declaration

`clusters/dev/apps/helmrelease.yaml` tells Flux what to deploy and how:

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: demo-app
spec:
  interval: 1m
  chart:
    spec:
      chart: ./demo-app
      sourceRef:
        kind: GitRepository
        name: flux-system
        namespace: flux-system
  values:
    replicaCount: 1
```

Flux watches this file. Any committed change triggers a Helm upgrade automatically — no manual `helm upgrade` needed.

## Making a GitOps change

This is the core of the workflow. To scale the app from 1 to 3 replicas:

1. Edit `helmrelease.yaml`:
```yaml
values:
  replicaCount: 3
```

2. Commit and push:
```bash
git add .
git commit -m "scale: increase replicas to 3"
git push
```

3. Flux detects the change (within ~1 minute) and reconciles:
```
GitHub commit → Flux source-controller pulls → kustomize-controller applies → helm-controller upgrades → 3 pods running
```

4. Verify:
```bash
kubectl get pods
```

Force an immediate sync without waiting:
```bash
flux reconcile kustomization flux-system --with-source
```

## How this maps to production (GKE)

This local setup is a direct mirror of a production GitOps pipeline:

| Local | Production |
|-------|------------|
| Kind | GKE cluster |
| Local Docker build | GitHub Actions → Docker build |
| Local image | Google Artifact Registry |
| `flux bootstrap` | FluxCD running in GKE |
| `kind load` | IAM-authenticated image pull from GAR |

The Helm charts, HelmRelease manifests, and Flux Kustomizations are identical — only the infrastructure underneath changes.
